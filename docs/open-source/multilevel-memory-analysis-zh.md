# Mem0 源码视角：多层记忆（Multi-Level Memory）到底是什么

> 基于 `README.md` 的 Introduction + Basic Usage 与 `mem0/memory/main.py` 的实现逻辑整理。

## 1) 先用一句话定义 Mem0

Mem0 不是一个“聊天模型”，而是一个可插拔的**记忆层**：在每次对话前做记忆检索，在提示词中注入相关记忆，让 LLM 回答；对话后再把新事实回写到记忆库，形成闭环。

这和 README 里的最小闭环一致：

1. `memory.search(...)` 检索相关记忆；
2. 将记忆拼进 system prompt；
3. 调用 LLM 生成回答；
4. `memory.add(...)` 写回新记忆。

---

## 2) “多层记忆”在源码里到底是什么意思

README 的“User / Session / Agent”在 Python SDK 中落地为三个可组合作用域：

- `user_id`：用户层（长期偏好、长期画像）
- `run_id`：会话层（某次任务、某个 ticket、某条线程）
- `agent_id`：智能体层（某个 agent 的工作策略、过程记忆）

Mem0 在实现上不是三套平行系统，而是统一到一个“作用域约束机制”：

- 写入时：作为 **metadata** 存到向量库 payload
- 检索时：作为 **filters** 过滤召回范围

并且至少要提供一个作用域 ID，否则报错（防止无边界检索/写入）。

---

## 3) 这是调用方来指定 User ID / Run ID / Agent ID 吗？

**是的，核心上是调用方指定。**

在 SDK API 设计上，`add(...)` 和 `search(...)` 都把 `user_id`、`agent_id`、`run_id` 暴露为入参。也就是说，业务系统（你的应用）决定当前一次调用属于哪个用户、哪个会话、哪个 agent。

### 你一般会在应用层这样分配

- `user_id`：来自账号体系（登录用户 ID、租户用户 ID）
- `run_id`：来自会话/任务体系（会话 UUID、工单号、工作流执行 ID）
- `agent_id`：来自 agent 编排层（planner、retriever、refund_bot 等）

### Mem0 在内部做什么

Mem0 不替你“猜真实业务身份”，而是：

1. 校验至少一个作用域 ID 已提供；
2. 合并成 metadata 和 filters；
3. 在检索/写入时严格按作用域生效。

所以，多层级是否有效，**关键在调用方作用域设计是否稳定且一致**。

## 4) 分“场景类型”介绍多层级

### 场景类型 A：仅 `user_id`（用户长期记忆）

**目标**：跨会话长期个性化。

- 典型数据：语言偏好、通知偏好、身体禁忌、常用地址。
- 典型收益：隔天、隔周再次对话仍可复用。
- 风险：没有 `run_id` 时，短期任务细节可能互相污染。

### 场景类型 B：`user_id + run_id`（用户 + 会话隔离）

**目标**：同一用户多线程并行、互不串线。

- 典型数据：一次旅游规划中的预算、路线、酒店偏好。
- 典型收益：召回更精准，减少“上个话题记忆串到这个话题”。
- 风险：如果 run_id 设计不稳定（频繁变化），会导致记忆碎片化。

### 场景类型 C：`user_id + agent_id`（用户 + agent 专属）

**目标**：多 agent 协作时保留 agent 的过程记忆。

- 典型数据：某 agent 的执行风格、偏好工具链、步骤模板。
- 典型收益：同一用户下，不同 agent 保持“各司其职”。
- 风险：agent_id 过细会造成记忆分散，过粗又会互相污染。

### 场景类型 D：`user_id + run_id + agent_id`（三层叠加）

**目标**：生产级多 agent + 多会话的精细化隔离。

- 典型数据：用户长期偏好 + 当前工单上下文 + 当前 agent 执行痕迹。
- 典型收益：全局个性化与局部任务聚焦同时成立。
- 风险：ID 体系治理复杂，需要平台层统一规范。

## 5) 分“业务逻辑场景”说明怎么落地

### 业务场景 1：AI 客服（工单制）

- `user_id`：客户 ID
- `run_id`：工单号
- `agent_id`：退款/物流/售后 agent

**逻辑**：

- 长期偏好（如通知方式）走 user 维；
- 当前工单状态走 run 维；
- 处理流程经验走 agent 维。

### 业务场景 2：医疗健康助手

- `user_id`：患者 ID
- `run_id`：本次就诊/随访 ID
- `agent_id`：营养师 agent / 问诊 agent

**逻辑**：

- 慢病长期信息用 user 维；
- 本次化验、处置建议用 run 维；
- 不同专业 agent 的表达和流程偏好用 agent 维。

### 业务场景 3：企业 Copilot（项目协作）

- `user_id`：员工 ID
- `run_id`：项目/需求单 ID
- `agent_id`：代码 agent / 文档 agent / 测试 agent

**逻辑**：

- 员工写作风格、技术栈偏好沉淀到 user 维；
- 项目决策、里程碑沉淀到 run 维；
- 各 agent 的执行策略沉淀到 agent 维。

## 6) 实际案例：电商客服系统

- 用户 `u_42`（`user_id`）
- 工单 `ticket_2026_031`（`run_id`）
- 退款处理 `refund_bot`（`agent_id`）

### 第 1 轮

用户：“我这个月第二次买错尺码了，想退款；另外我更偏好短信通知。”

- `search(query, user_id=u_42, run_id=ticket_2026_031, agent_id=refund_bot)`
- 组装 prompt，生成答复
- `add(messages, user_id=u_42, run_id=ticket_2026_031, agent_id=refund_bot)`

可沉淀记忆：

- user 维：短信通知偏好
- run 维：当前工单为尺码问题退款
- agent 维：退款流程先核验再发起

### 第 2 轮（同工单）

用户问：“退款进度如何？”

- run 维召回当前工单上下文；
- user 维召回通知偏好；
- 结果：回答既“对事”又“对人”。

### 第 3 轮（新工单）

新工单 `ticket_2026_032` 询问物流。

- 旧退款工单细节被 run_id 隔离；
- 用户长期偏好仍可继承。

这就是多层记忆的产品价值：**既记住你是谁（user），又知道你现在在处理哪件事（run），还知道当前是谁在执行（agent）。**

## 8) 常见误区与建议

### 误区 1：多层 = 三个 ID 都必须传

不是。至少一个即可；按业务复杂度叠加。

### 误区 2：run_id 可随便生成

如果每轮都变，记忆会碎片化；建议 run_id 与“业务任务单元”一一对应。

### 误区 3：agent_id 只是装饰字段

不是。它直接影响检索边界与记忆归属；在多 agent 系统里非常关键。

### 建议：ID 治理规则先行

在接入前先定义：

- user_id 来自哪里、是否跨系统统一；
- run_id 生命周期（何时创建/关闭）；
- agent_id 命名规范（固定枚举优于自由文本）。

这样多层记忆才能真正“可控、可解释、可维护”。
