# 记忆作用域场景解析

本文对三个常见作用域进行统一说明，并重点回答：

> 场景 C（`user_id + agent_id`）是否意味着“多个 agent 都能看到同一个用户长期记忆”？

简短结论：**不完全是**。`user_id + agent_id` 本质上是“**用户维度下，再按 agent 维度切分**”。只有在检索时不加 `agent_id` 限制（或显式做跨 agent 聚合）时，多个 agent 才会共享同一用户的长期记忆池。

---

## 场景 A：仅 `user_id`（用户长期记忆）

**适合**：跨天、跨会话都要保留，并且可被该用户下所有流程复用的信息。

- 典型内容：饮食偏好、语言偏好、过敏史、常用地址。
- 检索特性：只要带同一 `user_id`，通常都能召回。
- 优点：个性化能力最强，复用率最高。
- 风险：如果业务线程很多，容易出现“召回过宽”，需要配合 metadata 或 query 约束。

**一句话**：A 是“用户级共享长期记忆池”。

---

## 场景 B：`user_id + run_id`（用户 + 当前线程）

**适合**：同一用户有多条并发任务线，需要严格隔离上下文。

- 典型内容：
  - 线程 1：东京旅行规划
  - 线程 2：Q4 营销方案
- 检索特性：带相同 `run_id` 才召回该线程记忆。
- 优点：最大化降低串线（A 线程信息污染 B 线程）。
- 风险：跨线程复用变弱；需要你设计“何时提升到 user 级长期记忆”。

**一句话**：B 是“用户下的任务分区记忆”。

---

## 场景 C：`user_id + agent_id`（用户 + 特定 Agent）

**适合**：多智能体协作，但每个 agent 有独立流程/风格/中间偏好。

- 典型内容：
  - 退款 agent：退款规则解释偏好、证据收集步骤
  - 物流 agent：物流追踪口径、催件流程偏好
- 检索特性：同一 `user_id` 下，只有匹配 `agent_id` 的记忆会优先命中。
- 优点：保留用户背景的同时，避免 agent 之间过程性记忆互相干扰。
- 风险：如果把“全局用户事实”也只写在 `user_id + agent_id` 下，会造成其他 agent 看不到。

**一句话**：C 是“用户级上下文 + agent 私有工作记忆”。

---

## 你提出的问题：场景 C 到底是不是“多个 agent 共享用户长期记忆”？

### 结论拆解

1. **如果写入时带了 `user_id + agent_id=A`，检索也带 `agent_id=A`**：
   - 这是 A agent 的私有子空间；B/C agent 默认看不到。  
2. **如果写入是仅 `user_id`（不限定 agent）**：
   - 所有 agent 只要按 `user_id` 检索，通常都可共享这部分长期记忆。  
3. **如果想“既共享用户长期记忆，又有 agent 私有记忆”**：
   - 推荐“双层写入/双通道检索”策略（见下节）。

因此，你的理解可以修正为：

- `user_id + agent_id` **不是天然全员共享**；
- 它是“同一用户下按 agent 分桶”；
- 要“多个 agent 都看到长期记忆”，应把这类长期事实放在 `user_id` 公共层，agent 相关流程记忆放在 `user_id + agent_id` 私有层。

---

## 推荐落地策略（生产可用）

### 1) 分层建模

- **公共层（Shared）**：`user_id`
  - 存“稳定、可复用、跨 agent 都应知道”的长期事实。
- **私有层（Private）**：`user_id + agent_id`
  - 存该 agent 的执行偏好、工作步骤、中间结论。
- **线程层（Thread）**：`user_id + run_id`（可选）
  - 存当前任务临时信息，任务结束可衰减或清理。

### 2) 检索顺序

在 agent 响应前，建议按优先级拼接上下文：

1. 先查 `user_id + agent_id`（拿到该 agent 的专属上下文）
2. 再查 `user_id`（补充用户长期事实）
3. 若有线程语义，再查 `user_id + run_id`

这样既减少串线，又不丢用户长期个性。

### 3) 写入规则

- 用户稳定偏好（如“中文回答”“对花生过敏”）→ 写入 `user_id`
- agent 专属流程记忆（如“退款先核订单再验签”）→ 写入 `user_id + agent_id`
- 本次任务中间状态（如“已联系酒店等待确认”）→ 写入 `user_id + run_id`

---

## 常见误区

- **误区 1**：所有内容都写 `user_id + agent_id`。  
  结果：用户长期事实无法被其他 agent 复用。

- **误区 2**：所有内容都只写 `user_id`。  
  结果：多 agent/多线程下召回过宽，容易串线。

- **误区 3**：检索只查一个层。  
  结果：要么丢共享背景，要么丢 agent 专属上下文。

---

## 最终回答（针对你的问题）

是的，**“多个 agent 都能看到用户长期记忆”这个目标可以实现**；但前提是这部分记忆要放在**仅 `user_id` 的共享层**，而不是只放在某个 `user_id + agent_id` 子空间。

而场景 C 的核心价值是：在共享用户背景之上，为每个 agent 保留各自的过程性记忆，避免互相污染。
